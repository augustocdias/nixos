# Voice services reference

Read before changing voice routing, models, translation, Laya evaluation, or Open WebUI and its tools. The [macmini host reference](system.md#macos-nix-darwin-host--macmini) owns launchd daemon setup, ollama environment, model loading, and logging failure modes. Source files remain authoritative for current values. Historical measurements below describe their recorded test conditions, not a fresh verification.

## Laya

A local fast path for voice commands, in front of the ollama agent. Two halves:

- **Server** (`modules/services/laya/laya.nix`, macmini): `laya.serve` from the `laya` PyPI wheel, a launchd daemon on `0.0.0.0:8000`, `LAYA_DEVICE=mps`. It speaks TypeSafe's `/v1/systemone` protocol. **No auth, no sops, deliberately**: it is LAN-only and can only score questions, never act. Only the `multilingual` checkpoint (mmBERT, 322M) is loaded. `LAYA_REVISION=reviewed` pins the HF bundle to the SHA that laya release vetted, so weights only move with a package bump; they are fetched into `/var/lib/laya/hf` on first start (~1 GB). No `trust_remote_code`.
- **Translator** (`modules/services/libretranslate/libretranslate.nix`, macmini): LibreTranslate with only the en\<->pt Argos models (`--load-only en,pt`, ~160 MB, fetched on first start), launchd daemon on `0.0.0.0:5001`, no auth. Port 5001 avoids macOS AirPlay's listener on 5000; AirPlay stays unchanged. All argos paths go through `HOME` + `XDG_*_HOME`, every one of them pinned to `/var/lib/libretranslate` (under a systemd user unit `HOME` was overridden and models landed in the real home). ~1 GB resident, ~80 ms per command.
- **Client** (`modules/services/home-assistant/laya/`, Pi): our own conversation agent, domain `laya`. It does not derive from `allenporter/home-assistant-jev`/`-laya`, whose BM25 retrieval, English stopwords and unit-word regexes break on pt-BR before the model sees anything. Config flow: server URL, translator URL (empty disables it); options: fallback agent, confidence and compound thresholds. Anything it is unsure of, questions, and multi-step requests go **unchanged** to the fallback (ollama) agent via `conversation.async_converse`; laya being down escalates too.

The client supports reconfiguring both URLs without replacing its config entry or changing options. Existing entries retain their saved translator URL until reconfigured. Deploy the server on port 5001 first, then deploy the updated HA component and reconfigure the existing Laya entry to `http://macmini.local:5001`. An isolated HA instance verified entry identity, unrelated data, and options survive this flow; the production URL migration remains pending deployment.

LibreTranslate scopes a `flask-swagger-ui` build override to its own dependency: 5.32.14 uses `pyproject.toml`, but the pinned nixpkgs recipe still invokes the missing `setup.py`. The override selects the declared setuptools backend without changing versions or disabling checks. The launch command names `libretranslate` explicitly because the package has no `meta.mainProgram`. Native Darwin build, packaged CLI startup, and Swagger HTML/JavaScript/CSS requests passed; service activation and live translation remain separate checks.

**Laya only chooses among options it is given; it never generates.** That shapes `pipeline.py`:

- Numbers are read from the text (`\d+([.,]\d+)?`, pt decimal comma); the chosen *action* decides the slot (brightness, position, temperature, volume). No unit words, so nothing is language-specific.
- Round 1: request kind (command / question / other), device kind, compound, portuguese. Round 2 (one request): the kind's *own verbs* (blinds: open / close / set position), asked twice with the options reversed — both must agree; plus the device, only when the text leaves more than one. Measured: a flat 13-way intent choice collapsed (pt requests landed on the vacuum).
- **Option keys are human text.** Laya renders an option as `"key: description"`, so `HassTurnOn: Turn on` / `light.x: Kitchen Light` fed identifier noise straight into the decision. Keys are now the labels; `Planner._ids` maps answers back.
- **Which device is grounded in the text, never chosen by the model alone.** The model confidently picked wrong rooms ("open Tobias's blinds" → bedroom at 0.88), and no threshold removes high-confidence errors. Names and aliases of entities and areas are matched as whole phrases (casefolded, accent-free, possessive `'s` dropped; a match inside a longer one is dropped, so "quarto do Tobias" is not the bedroom). A device must be named, or be the only one of its kind in the named room (or the house). A named device must sit in the named room, and settles its own kind. **Aliases are therefore what makes pt-BR work** — an entity with none ("Livia Light") is only reachable in English.
- **Translation feeds the model, never the grounding.** The model reads LibreTranslate's English; names and numbers are grounded in what was said first, and in the translation only when the original names nothing. Translation loses names ("luz da sala" -> "the room light", "escada" -> "ladder", "depósito" -> "warehouse") but keeps verbs, which is exactly the split. A down translator just passes the original through.
- **The request language is the pipeline's, not detected.** With one Assist pipeline per language (EN, BR) and conversation language `*`, HA sends the pipeline's STT language as `language` — and that same language overrides whisper's `--language auto` on every request, so a BR request really is Portuguese. It becomes LibreTranslate's `source` (`pt-BR` -> `pt`); `en` skips translation. Only `*`/missing falls back to LibreTranslate's detection, which called "desliga a luz da sala" English at 0 confidence. The fallback LLM always gets the original words.
- Numbers must fit the action both ways ("dim to 20%" answered "turn on" escalates). Area-wide requests ("all the lights") are not handled; they escalate.
- **Nouls are badly calibrated on this model** — one yes/no per area answered "yes, HWR" at 0.95 for nearly everything. Use choices for anything that matters.
- Entities are addressed as name + their own area (two exposed entities are both named "Hallway Light").

**Status: 0 wrong actions on the test set**, laptop CPU, live HA snapshot (with aliases), `cases.json` (45 utterances):

| checkpoint                 | set | ok    | escalated | WRONG | median  |

Remaining pt escalations are mostly the model's *verb/kind* reading of Portuguese (low confidence), which is what a translation layer would address. 45 cases is a small set: grow `cases.json` before trusting the zero. Re-measure on the macmini with `laya-eval/eval.py --home <snapshot> --url http://macmini.local:8000` before enabling it in an Assist pipeline; `-v` prints the per-question trace, `--translate http://macmini.local:5001` adds the translator, `--model english --head-max-len 384` compares checkpoints (the server must load it; english's window is 512 tokens). The snapshot is dumped fresh from HA into a temp file each time (exposed entities **with their registry aliases** — the first measurements left aliases out and understated both languages); `--selftest` needs none.

## Open WebUI

Self-hosted AI workspace on `macmini`, owned by the existing `open-webui` aspect. The listener remains **LAN-bound on `0.0.0.0:8080`**, not loopback-only. The declared configuration now requires password authentication before exposing Hermes tools; activation and end-to-end deployment gates remain separate from configuration changes. Existing LAN HTTP does not encrypt passwords or conversations.

- **`STATIC_DIR` must be redirected.** It defaults to a directory inside the package's own store path, and open-webui `shutil.copyfile`s the favicon, splash and loader into it on every start (`config.py:111,125,133,141`). Left alone it writes to a read-only store path. Same reasoning for `DATA_DIR`, `HF_HOME` and `SENTENCE_TRANSFORMERS_HOME`; all four live under `/var/lib/open-webui` and are created in `postActivation`.
- **`HOST`/`PORT` are not environment variables.** `serve` is a typer command whose `host`/`port` are CLI options defaulting to `0.0.0.0:8080`. Setting `env.HOST` is silently ignored and the app listens on every interface — so the bind address is passed as `--host`, not as env.
- **`ENABLE_PERSISTENT_CONFIG = "False"` is what makes this declarative.** At its default (`True`) the first boot seeds env-derived values into the `config` table and every later read comes from the database, so editing the Nix would silently do nothing. False makes the environment authoritative on every boot. The trade is the same one OmniWM's `settings.toml` makes: **settings changed in the admin UI no longer persist** — declare them in Nix instead.
- **Authenticated profile routing**: `WEBUI_AUTH=True`, signup disabled, direct Ollama access disabled. Two explicit OpenAI-compatible connections point to `/p/augusto/v1` and `/p/livia/v1` on loopback Hermes. Their `model_ids=["hermes-agent"]` and distinct `prefix_id` values yield `augusto.hermes-agent` and `livia.hermes-agent`. Keys enter only the runtime environment, not plists or store paths.
- **Fail-closed pre-start**: the wrapper waits for the signing secret, two initial passwords, and two personal gateway keys. `_bootstrap.py` refuses to migrate while the old listener is running, backs up the existing SQLite database to `webui.db.pre-hermes.bak`, runs packaged migrations, then uses the Auths/Users/Models DAL. Missing credentials, missing/conflicting identities, or bootstrap errors prevent the LAN listener from starting. Augusto retains UUID `c6536b76-6232-416e-97c7-7d75b38133d8` and history, with login `augusto@localhost`; Livia uses `livia@localhost` as an ordinary user. A runtime identity journal makes initialization resumable without resetting later password changes. Initial password migration revokes existing account sessions.
- **Private model records**: each base model belongs to its corresponding user's UUID, with `base_model_id=null` and `access_grants=[]`. Admin picker bypass, model bypass, and admin chat access are disabled. This is trusted-admin application separation, not isolation from Augusto's server administration rights. WebUI 0.12.3 still permits administrators to call other models directly through its API; Livia must be denied Augusto's model.
- **MCP/PostHog compatibility**: WebUI 0.12.3 declares MCP 1 and imports `streamablehttp_client`, removed by MCP 2. Its private Python scope selects nixpkgs' retained `mcp_1` (1.29.0). This also avoids PostHog 7.71.0's MCP-2-specific test failure and broken marker. No global package override, metadata suppression, test disabling, or vendored test patch remains.
- **First system-level sops on macmini.** The repo's `secrets` aspect is home-manager-only, so this imports `sops-nix.darwinModules.sops` and points `age.keyFile` at `/Users/augusto/.config/sops/age/keys.txt` — the key the HM aspect already provisions, readable by root. No second key to manage, but activation now depends on a path inside the user's home.
- **Retrieval and search**: `VECTOR_DB` and `RAG_EMBEDDING_ENGINE` retain embedded ChromaDB and local sentence-transformers (`all-MiniLM-L6-v2`) on CPU. Web search remains DuckDuckGo through `ddgs`. Model downloads populate `HF_HOME`; these are separate from the loopback-only Hermes/Honcho inference routes.

Native Darwin build and isolated database-copy checks verified account/history preservation, password-change persistence, session revocation, and private model ownership. A real isolated WebUI server required login, disabled signup, and returned only each account's own model. Livia's direct requests for Augusto's model failed through both chat API routes. Live gateway-backed chat completed after the Honcho encoding repair described below. Browser-session verification was blocked by the browser daemon; memory recall, boot lifecycle, and shared-model capacity remain deployment gates.

### Tools

Tools remain rows in WebUI's `tool` table. `_tools.nix` pins their sources, and the existing `open-webui-tools` daemon imports them through the authenticated HTTP API.

- **The attr name in `_tools.nix` is the Open WebUI id**, which is the table's primary key and is caller-supplied — not generated. It must equal the id of the row already installed or a second, functionally-duplicate tool appears. This is why `wiki.py` is declared as `wikipedia_tool`. The id is also lowercased and `.isidentifier()`-checked upstream, so `ask-user` has to be `ask_user`.
- **Upsert is enforced by the API, not by the script.** `create` refuses an id that exists (400 `ID_TAKEN`) and `update` refuses one that does not (401 `NOT_FOUND`), so listing the ids first and picking the matching call is idempotent. `valves` is a separate column that `update` never writes, so tool configuration survives. `specs` and `meta.manifest` are re-derived from the source on every write, which is why a bare `.py` is a complete representation.
- **The importer mints its own session token.** It signs HS256 with `WEBUI_SECRET_KEY` and reads the active administrator's ID and current `auth.session_stamp` read-only from SQLite. WebUI 0.12.3 checks that persistent stamp before optional Redis revocation, so password/session migration invalidates older tokens even without Redis. No new API key is provisioned.
- **`ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS = "False"`** — a tool's frontmatter `requirements` are otherwise pip-installed at create time into the read-only store, which is what made `osm` fail to install. Its two requirements are supplied through the package's python env instead: `pygments` is already a dependency, `openrouteservice` is added by `overridePythonAttrs`. Both are top-level imports in `osm.py`, so neither is optional.

## Honcho

The macmini-only `honcho` aspect owns native PostgreSQL 17 with pgvector, the Honcho API (`127.0.0.1:8001`), and one deriver worker. Its Python 3.13 environment comes from the locked source's `uv.lock`; its environment version comes from that source's `pyproject.toml`. The uv2nix builder is shared with Hermes and follows Hermes's existing nixpkgs and pyproject-nix inputs. Honcho's Linux and Darwin derivations evaluate with warnings treated as errors. The virtual root project stays on `PYTHONPATH`; runtime installation is not used.

PostgreSQL runs as existing `_postgres`, without a TCP listener, under `/var/lib/honcho/postgresql`. Peer mappings permit `_postgres` to bootstrap as `postgres` and `augusto` to connect as non-superuser `honcho` only to database `honcho`. Bootstrap preinstalls `vector`, `pg_trgm`, and `btree_gin` in that database. Unexpected ownership, database ownership, role privileges, or PostgreSQL major version fail closed; initialization never overwrites a nonempty directory.

Honcho requires a UTF-8 database. Initialization passes `initdb --encoding=UTF8`, and database creation explicitly uses `ENCODING 'UTF8' TEMPLATE template0`. macOS with locale `C` otherwise defaults to `SQL_ASCII`; psycopg then returns catalog names as bytes, causing the old extension check to fail even when all extensions exist. Both bootstrap and application readiness now reject an existing non-UTF-8 database with an explicit migration error rather than silently converting it. Never reinitialize a populated store. For an empty failed first deployment, stop the API/worker/Hermes jobs, preserve the old database under a rollback name, create the UTF-8 replacement and extensions, then restart those jobs. This live repair requires privileged PostgreSQL access; native isolated tests verified initialization, rerun, multilingual text, and safe rejection of a pre-existing `SQL_ASCII` database.

The empty first-deployment database was preserved as `honcho_sql_ascii_backup` during the approved live repair. Verification confirmed the replacement reports `UTF8`, Honcho health returns 200, both personal Hermes model routes accept their own keys and reject cross-profile keys, and a real WebUI assistant response completed with text and no recorded error. Ollama reported `qwen3.5:9b-mlx` at context 262144 alongside the compact embedder; this is not a full occupied-context capacity test.

API startup waits for the application role and extensions, verifies that local `qwen3-embedding:0.6b` returns 1024 finite numbers, runs migrations, then runs upstream's empty-vector-table dimension bootstrap. Existing populated embeddings cannot be resized. API startup fails on any error. The worker waits for live API/database readiness, creates `hermes-augusto` and `hermes-livia`, persists scoped keys under `/var/lib/honcho/app/keys`, checks authorized access and cross-workspace rejection, then starts derivation. No stale readiness file controls startup.

All nine generation roles use loopback Ollama and inherit `services.ollama.model`, declared in `modules/services/ollama/ollama.nix`. The same value drives the Ollama loader and Hermes; change the default there rather than editing each consumer. Embeddings retain the separate 1024-dimensional compact model, so no vector migration or memory reset is required. The deployed extraction configuration sets `DERIVER_MODEL_CONFIG__THINKING_EFFORT=none` so its output budget can produce structured facts instead of reasoning; both running Honcho processes were checked before the model change. An authenticated API, real queue/worker, local Qwen MLX inference, and disposable PostgreSQL cluster verified correct saved facts and recall in a fresh conversation without repeating the introduction. Production subsequently completed all twelve representation jobs and held 202 non-deleted conclusions at verification. These are Qwen-era checks, not GPT-OSS quality or latency results. Redis, Sentry, hosted telemetry, and metrics listeners are disabled. `honcho_jwt_secret` is SOPS-managed and readable by `augusto`; admin JWTs remain transient bootstrap credentials, never profile credentials.

Verification exercised native Darwin package build, Linux PostgreSQL bootstrap/rerun, real migrations, 1536-to-1024 empty-store bootstrap/rerun, live API scoped-key provisioning/rerun, and cross-workspace rejection. These checks do not establish macOS boot lifecycle, model inference quality, or shared-host capacity.

For an apparently empty memory, inspect persisted message counts, `GET /v3/workspaces/{workspace_id}/queue/status`, conclusion counts, and terminal queue errors separately. The observed introductions reached `messages`, but two representation jobs failed with `StructuredOutputError`, `failure_class=ValueError`, and `payload_bytes=0`; their stack entered the truncated-completion repair path. Terminal failures are marked processed and are not automatically replayed by restarting the worker. After verifying the extraction fix, recovery locked and checked only original queue IDs 1 and 2, including workspace, task type, message IDs, and failure fingerprint, then reset their processed/error fields. The existing worker completed both in about 85 seconds; message count remained 24, and all twelve representation jobs finished without errors. Do not resend introductions or reset unrelated queue rows to recover failed derivation.

`hermes -p <person> honcho status` previews peer cards and an AI representation; it is not a complete view of saved conversations or conclusions. Cards are produced by a later dream stage, whose pinned defaults require 50 explicit observations and 60 minutes of session inactivity, with an eight-hour minimum between dreams. An empty card alone does not prove ingestion or learning failed.

The isolated synthetic introduction produced six stored conclusions across the two observer relationships in roughly 9–13 seconds. A fresh session retrieved the saved name, city, and tea preference through the actual context API. A separate manual `card_refresh` completed but left the preview card empty, so card-generation quality is not established by these checks. In a controlled structured-output request, default thinking consumed its entire 128-token test budget without final JSON; `reasoning_effort=none` returned the correct JSON. The production failures used the larger configured extraction budget, so the small-budget test demonstrates the failure mechanism rather than replaying the private introductions.

## Hermes Agent

The macmini-only `hermes-agent` aspect uses upstream's Nix `messaging` package. Its package version is `unstable-<locked short revision>` because upstream's project metadata uses the placeholder `0.0.0`. The extra `honcho-ai` SDK is built for the package's own Python; its version comes from Honcho's locked source, and its declared runtime requirements are checked against Hermes's sealed environment without duplicate dependency copies. Upstream's collision check remains enabled. The separately locked directory plugin is linked into each personal profile; there is no runtime pip/npm installer. Bootstrap also links rtk's upstream `rtk-rewrite` plugin (from `pkgs.rtk.src`) into each profile and adds it to `plugins.enabled`. It adds to the list rather than replacing it, so locally enabled plugins stay on. `pkgs.rtk` is first on the daemon's sanitized `PATH`. The plugin rewrites `terminal` commands (`git status` to `rtk git status`), and Hermes's dangerous-command detection runs on the rewritten command. See [Coding agents](coding-agents.md#rtk-shell-output-compression).

Caveman and Ponytail reuse the same pinned upstream sources as the coding harnesses. Each personal profile receives a Nix-owned `skills/caveman-bundle` symlink containing all nine Caveman skills; `/caveman`, `/ultracave`, and `/megacave` opt into the upstream styles. Caveman's native Hermes integration is skill-only, not an always-on hook. Ponytail loads its native Python plugin and six bundled skills; its upstream default is `full`, with `/ponytail lite|full|ultra|off` controls. No source patches force activation or override stop controls. Existing enabled plugins are preserved, learned skills remain writable outside the managed bundle, and bootstrap refuses to replace an unmanaged directory at a managed link path. Isolated native Darwin checks exercised bootstrap/rerun, both profiles' CLI skill discovery, Caveman skill loading, Ponytail context injection and mode switching, same-process profile mode isolation, and preservation of local plugins, channel tokens, memories, and skills. Service activation remains a separate rebuild step.

**Updates:** Hermes, Honcho, the Honcho directory plugin, and uv2nix use unversioned GitHub input URLs. Exact revisions and hashes live only in `flake.lock`; ordinary [`nix flake update`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake-update) advances them without `nix-update` or manual version edits. These track upstream default branches, not automatically selected stable release tags. The policy change preserved all previously tested locked sources; a throwaway copy verified that a normal targeted flake update advances all four inputs. New upstream API or dependency incompatibilities can still require configuration changes.

Upstream's [Nix setup](https://hermes-agent.nousresearch.com/docs/getting-started/nix-setup) includes a Home Manager module, but its macOS service is a LaunchAgent. This deployment needs a boot-time system LaunchDaemon, so only service/profile glue is local. One foreground `hermes gateway run` runs as `augusto`, with a sanitized environment and host control home `/Users/augusto/.hermes`. `gateway.multiplex_profiles=true` serves independent `augusto` and `livia` profiles below `profiles/`, using upstream profile creation without cloning. No extra OS account or TUI configuration is required.

The same packaged Hermes CLI is installed through macmini's `environment.systemPackages`; no second installation is needed. After activation, use `hermes -p augusto gateway setup` or `hermes -p livia gateway setup` for channel configuration, and `hermes -p <person> whatsapp` for WhatsApp pairing. Keep the existing system LaunchDaemon: do not install another user gateway. Restart the managed service with `sudo launchctl kickstart -k system/org.nixos.hermes-agent` after changing channel settings.

`modules/services/hermes-agent/SOUL.md` is the shared declarative persona source. Bootstrap writes a separate mode-0600 copy into each personal profile; it does not share mutable files or copy personal memories between profiles. Edit the tracked source and rebuild to change both personas. Local edits to either managed `SOUL.md` are replaced on the next gateway start; start a fresh chat to use the new persona.

All three configurations inherit loopback `services.ollama.model` (currently `gpt-oss:20b`) from `modules/services/ollama/ollama.nix`, with configured context 65536 and main-model compression. Both personal profiles' context limits were verified with the previous Qwen deployment. Only the host enables the API listener (`127.0.0.1:8650`). Each personal `.env` owns a distinct SOPS-managed API key; runtime `honcho.json` explicitly includes its stable workspace key, with 2048-token retrieval, one low-reasoning dialectic pass every five turns, and independent mutable memories/sessions/skills/cron state. Missing credentials or failed authorized Honcho access block startup.

Model changes require a rebuild, restarting the affected services, and a fresh Hermes conversation. GPT-OSS end-to-end Hermes speed has not been verified here. Home Assistant's direct Ollama conversation and AI-task models are UI-managed config subentries, not part of the macmini Nix manifest; check their model selections separately.

Latency diagnosis must distinguish startup, memory retrieval, model scheduling, prompt processing, and output generation. Pinned Hermes discovers MCP servers concurrently; asynchronous Honcho recall can issue background model requests, so a background memory request can still compete with the main chat. Historical TUI metadata recorded roughly 19K input tokens, not a tiny greeting-sized request. A synthetic request of that size spent about 88 seconds processing input on the rebuilt production MLX server before its first word; see [macmini resource verification](system.md#macos-nix-darwin-host--macmini). An actual authenticated personal-profile gateway request with a 96-character diagnostic message then started reasoning at 147.270 seconds and completed the correct five-character reply at 149.274 seconds. Session metadata recorded 19,832 input tokens and 27 output tokens. Ollama reported a 19,835-token prompt with only three cached tokens; prompt progress occupied roughly 95 seconds. The preceding roughly 50-second interval included a separate 4,945-token model request, but no per-stage Hermes trace was collected to attribute that whole interval. This verifies substantial current end-to-end latency, not the exact cause of every historical 5–10-minute timeout. Use metadata-only timing output; raw prompts, message contents, credentials, and Honcho request URLs can contain private data.

A subsequent authenticated second turn explicitly resumed the same diagnostic session and took 618.560 seconds to begin reasoning and 630.329 seconds to finish the correct reply. Cold-start prompt processing alone therefore does not explain the observed delay. Concurrent operational logs showed multiple model responses taking roughly ten minutes, with both successful and canceled requests. Honcho background cycles reported 10–18 tool calls, roughly 95K–183K aggregate input tokens, and approximately 8–17 minutes elapsed. These are whole-cycle totals, not one uninterrupted model request; foreground requests can compete between their constituent calls. The exact deployed Ollama MLX runner serializes requests, regardless of the configured parallelism value; see [MLX scheduling limitation](system.md#macos-nix-darwin-host--macmini). Choosing between a controlled alternative-model benchmark and reduced background reasoning is a latency-versus-capability tradeoff. Neither change has been applied or demonstrated as a latency fix.

Bootstrap merges Nix-owned configuration into each existing YAML mapping instead of replacing channel settings. It updates `.env` atomically while preserving channel tokens, sender allowlists, and other local settings. The `API_SERVER_*` namespace remains Nix-owned: only the host gets listener settings, while personal profiles retain their own managed API key/model name. Malformed existing YAML fails closed without overwriting it. Native isolated checks exercised bootstrap/rerun, persona enforcement, channel preservation, private file modes, independent memories, CLI lookup through PATH, and real gateway authentication after rendering credentials.

Both personal profiles receive [Context7](https://github.com/upstash/context7) over its public HTTP endpoint and the existing Home Assistant MCP server over its authenticated webhook. NixOS, the Linux host bridge, and work MCPs (Notion, Linear, Datadog) are not added. Context7 uses anonymous access with lower rate limits; no npm installer or additional local MCP server is required.

SOPS entries `hermes_home_assistant_mcp_url` and `hermes_home_assistant_token` supply the private webhook URL and a dedicated long-lived token named `Hermes Agent`, owned by the existing `HA-MCP Server` administrator account. Bootstrap renders their SecretRefs into each personal profile's private `.env`, never into the Nix store or the host control profile. The token lasts 3650 days and can be revoked from its Home Assistant account. Both profiles share this household access, not separate HA permissions. The existing connection uses HTTP on the trusted LAN; do not expose it or its credentials to untrusted networks.

Pinned Hermes's generic config loader warns about `${env:NAME}` before CLI startup loads the profile's `.env`, even when MCP subsequently resolves the credential correctly. Native `${NAME}` references permit deferred MCP resolution without that false warning; unresolved remote URL/header references still fail closed at connection time. Credentials remain profile-local, not exported into the host control environment.

Unattended calls fail closed. Open WebUI's OpenAI-compatible chat route cannot answer these approvals, so use an approval-capable Hermes surface for HA changes. Native isolated checks verified both profiles' SecretRef resolution, live Context7 documentation lookup, live HA state reads, unattended write rejection, and preservation of a locally added disabled MCP entry. No device actions were performed.

For durable secret management, store static channel credentials such as Telegram bot tokens in SOPS and wire their runtime secret paths into this service for the owning profile; merely adding an encrypted key does not inject it into Hermes. Wizard-created credentials remain local in that profile's private `.env` until this wiring is added. WhatsApp linked-device session state stays in the profile's private `platforms/whatsapp/session` directory, not in a Nix derivation or plaintext repository file. Pairing and external messaging require the user's account/phone and were not exercised by the native configuration smoke.

Profile endpoints are `/p/augusto/v1` and `/p/livia/v1`. Pinned Hermes's prefixed `/models` responses advertise profile names, even with `API_SERVER_MODEL_NAME=hermes-agent`; WebUI connections must declare `model_ids=["hermes-agent"]` explicitly rather than infer advertised IDs. Native packaged gateway smoke verified both prefixed model-list routes and rejected cross-profile and host keys. This proves ingress scoping, not memory recall or inference quality.

# Coding agents reference

[Herdr](herdr.md) owns terminal lifecycle and sidebar integration.

## Harnesses and shared pieces

- **omp** (oh-my-pi) is the personal harness: aspect `omp` in `user-base` (laptop and macmini), plus `omp-jail` in `user-linux`.
- **Claude Code** is the work harness: aspects `claude-code` and `claude-code-jail`, included only by the `work` aspect (laptop).

Shared material lives in `modules/programs/agent-shared/` and `modules/programs/agent-jail/`:

- `agent-shared/agent-shared.nix`: shared packages, included by both harness aspects. It installs terminal-browser from the same `llm-agents` input as Herdr.
- `agent-shared/_lib.nix`: prompt bodies are frontmatter-free, and each harness renders its own frontmatter through `withFrontmatter`, because the harnesses disagree on keys. `contextText` is `context.md` plus the style rules in `style/`.
- `agent-shared/_bash.nix`: the bash ruleset, translated by each harness's `_permissions.nix`. See [Approvals](#approvals) for why overrides may only narrow.
- `agent-jail/_mk-jail.nix`: the bubblewrap jail used by both harnesses. `agent-jail/jail-context.md` is loaded only inside the jail.
- `agent-jail/_host-query/` backs the `host_*` tools; `agent-jail/host-mcp.py` exposes them to both harnesses as a stdio MCP server.
- `agent-jail/_herdr-relay/` publishes restricted sidebar metadata to the launching Core terminal.

Ponytail and Caveman load only from the adapted copies in `agent-shared/style/`, including household Hermes. Neither has an upstream flake input or installed plugin.

Both harnesses install the terminal-browser skill from `agent-shared/skills/terminal-browser/`. It launches browsers in Core terminals rather than using the browser's legacy Herdr TUI split adapter. The skill owns browser/tab selection, screenshots and cleanup while preserving each harness's sandbox and approval rules.

## Development skills

Both harnesses install every skill under `agent-shared/skills/` from one bundle (`agent-shared/_skills.nix`), which copies the shared `WORKFLOW.md` into each installed skill root so companion reads stay inside that root. Licenses and attribution live only in `third-party/` and are not installed.

Skill additions and upstream refreshes are human-owned. Keep explicitly installed skill text in this repository instead of sourcing it from an updating package. jgrep's work-only skill lives in `modules/services/work/skills/jgrep/`, separately from its executable. Hermes's own bundled and plugin-provided skills remain an explicit exception: they still follow Hermes and plugin updates. This policy does not freeze executable prompts, tool descriptions or MCP responses.

The manual `orchestrator` skill runs `implement-spec` with separate omp or Claude sessions in Herdr Core terminals. It reuses the spec workflow's dependency graph, evidence gates and progress file rather than adding a service or board. Invoke Claude `/orchestrator` or omp `/skill:orchestrator` with the spec. `hermes-agent/_work.nix` requests a bundle that excludes this skill, including from Hermes's filesystem discovery.

Core terminal state is a notification, not acceptance evidence. The skill records terminal identities for recovery, preserves one writer per checkout and returns approval blockers to the human. Separate Linux jails must prove access to the supplied supporting workspace; a parent's path or grant is not inherited authority.

Verify both skill bundles and rendered Home Manager skill paths after changes. Exercise Core launch, wait, evidence collection and owned-terminal cleanup with isolated workers. Fresh-session discovery and real spec completion need separate checks after activation.

Skills specific to this repo (`den-module`, `nvim-plugin`, `sops-secrets`) live in `.claude/skills/` and are not installed by Nix. Claude Code reads that folder as project skills, and omp reads it through its built-in `.claude/skills` provider.

- **Provenance**: the Matt Pocock skills are local curated copies, not a flake input. `third-party/mattpocock-skills/UPSTREAM.md` records the reviewed revision and the local adaptations. Updates are deliberate copy-and-review operations verified in both harnesses. pstack-derived skills and the ideas folded into house skills are listed in `third-party/pstack/UPSTREAM.md`, with the reviewed revision. `rust-best-practices` is written from the Microsoft and Rust API guidelines. `git-conventions` is local.
- **Routing and workspace contract**: `skills/WORKFLOW.md` owns invocation (including which skills are manual-only), `.dev-skills/` workspace resolution, delegation, and artifact handling. `agent-shared/context.md` is the always-loaded minimum: the `cd` rule and the `git-conventions` pointer, followed by `agent-shared/evidence.md`, the evidence rules Hermes souls also append; everything else lives in `WORKFLOW.md` or the skills. Edit those files, not this doc, when the contract changes.
- **Research**: the shared `research` skill combines the existing workspace/delegation contract with the evidence method from `hermes-researcher-agent`; provenance lives in `third-party/hermes-researcher-agent/UPSTREAM.md`. omp, Claude Code and Hermes consume the same research source, so edit the shared skill rather than creating a Hermes-only copy. Its companions stay inside the skill root. Quick lookups stay short; substantial investigations keep their source ledger in the same findings file. Authorized internal research remains supported, but private context must not enter public queries.
- **Research verification**: build the shared skill bundle and exercise its installed references and template. Check a single-authority fact, a repository comparison, copied announcements, blocked sources and authorized local-code research. Verify discovery in fresh sessions of all three harnesses after activation; a bundle build alone does not prove session discovery or research behavior.
- **Boundaries** that every skill workflow keeps:
  - `git-conventions` owns the upfront agreement for branch, worktree, commit, push, and PR ownership. Read-only work needs none.
  - Existing approvals stay mandatory. Routine delegation never authorizes published rewrites, merging PRs, destructive cleanup, or repository-setting changes.
  - Every commit is signed when it is created: with the agent key in a session holding the signing grant, otherwise through `host_exec`. A pre-push `git verify-commit` over every outgoing commit gates each push.
  - The parent owns credentials, signed commits and pushes (through Linux `host_exec`), refs, tracker writes, and shared progress. Required `host_ssh_agent` approval comes before any subagent starts.
  - Delegates receive the parent's absolute `.dev-skills/` workspace, even outside their own Git root. One writer owns each checkout.
  - `.dev-skills/` artifacts never enter implementation commits or pushes. Local exclusion is not encryption or backup.
  - Generated wizards run on the host, by the human.
- **Review axes**: `code-review` runs Standards, Spec and Proof. Proof adversaries run the real code and keep repros in the workspace; the parent reruns every finding. The extended panel of extra agents or models is agreed per run like the `git-conventions` agreement, and an unattended run uses the default adversary alone. Hermes inherits all three axes because `sdlc-review` loads `code-review`.
- **Diagnosis is not fixing**: `diagnosing-bugs` ends at `debug/<slug>/diagnosis.md`. Inside a workflow it returns the diagnosis to the assignment, which fixes in-scope causes or blocks for out-of-scope ones; invoked directly it writes a `to-spec`-shaped `plan.md`.
- **Project skills**: per-project skills (generated verification skills) live in `<repo>/.dev-skills/skills/`. Claude Code reads only `.claude/skills` and Hermes only `.agents/skills` or `.hermes/skills` under a trusted root, so `setup-dev-skills` links `.claude/skills` and `.agents/skills` to that folder and excludes the links locally. Hermes needs `hermes -p <profile> skills trust <root>` per profile; bootstrap's deep merge keeps `skills.trusted_project_dirs`. Links are used because no harness accepts a Git-root-relative skill folder from one global setting: omp's `skills.customDirectories` resolves relative paths against the launch directory, and Claude Code and Hermes have no such setting.
- **omp task isolation is off** (`task.isolation.enabled = false`): its automatic snapshots are not permission-controlled Git worktrees, and `implement-spec` assigns approved worktrees itself.

## Agent sandbox (Linux only)

On Linux, `omp` and `claude` are the jail: `_mk-jail.nix` wraps each package with bubblewrap through the `jail-nix` combinator library and installs it under the original binary name. Darwin has no sandbox and relies on the bash allowlist alone. `agent-jail/jail-context.md` is the agent-facing contract for writable areas, host access, SSH, signing, and deletion. Keep it in sync when the jail changes.

Gotchas behind the jail's design:

- **Writes outside the binds vanish.** `/`, `/etc`, `/tmp`, and `$HOME` are per-session tmpfs, so a successful write there proves nothing. Per-harness state (grants, logs) lives in `~/.local/share/<name>-jail/`.
- **Linked worktrees need the git-common-dir bind.** The launcher binds `git rev-parse --git-common-dir` when it differs from the git dir; without it git fails outright.
- **No setuid.** bwrap sets `PR_SET_NO_NEW_PRIVS` unconditionally, so in-jail `sudo nixos-rebuild` cannot activate the host. Approved `host_exec` and authorized remote deployment still work.
- **`NIX_REMOTE=daemon` is mandatory.** The uid map makes the store look user-owned and tricks nix into single-user mode. Because `trusted-users = root`, a client cannot disable the build sandbox, which is why `nix build` is safe to allow inside.
- **No curated toolbelt.** `/nix/store` is bound read-only and PATH comes from `/run/current-system/sw` and `/etc/profiles/per-user/<user>`. Curating tools would not be a boundary, since every store binary is reachable by absolute path.
- **The launcher's environment is inherited.** jail-nix's `base` ends with `--clearenv`, so the jail uses `reset` and rebuilds the pieces without it. Core-launched commands do not necessarily have the credentials loaded by an interactive shell. `_mk-jail.nix` fills missing or empty `GH_TOKEN`, `TYPESAFE_API_KEY` and `OLLAMA_CLOUD_API_KEY` from their sops files before entering the jail, preserving nonempty inherited values. An unreadable or empty required secret stops launch with a variable-name error. Only paths enter the Nix store; values are exported at runtime and the secret directory is not mounted. The shared loader covers omp, Claude and Hermes. Other environment values still depend on the launcher. Consequence: `add-path` seeds from an empty PATH, so use `set-env "PATH" "…:$PATH"`.
- **`GPG_TTY` is removed twice**: unset in the first runtime block (before `pre` and host-query start) and `--unsetenv` in the final block (after caller overlays). gpg-agent keeps its own terminal and display state, so a missing `GPG_TTY` does not prove GUI pinentry. Do not flush caches or restart the agent just to force a prompt.
- **No gpg-agent socket.** The agent is a signing and decryption oracle: exposing it would let the jail sign as the user and decrypt every sops secret. With `signByDefault = true` in the read-only git config, ordinary `git commit` fails for lack of a signer. Signed commits go through `host_exec`, or through the agent key when the session holds the [signing grant](#signing-and-push-grant).
- **SSH comes from a relay, on approval.** `SSH_AUTH_SOCK` is unset at launch. `host_ssh_agent` makes host-query listen on `<grant_root>/ssh-agent.sock` and pipe each connection to the host's `S.gpg-agent.ssh` until host-query exits. It is a relay rather than `host_mount` because a socket seen through bindfs/FUSE cannot be `connect()`ed. `~/.ssh/known_hosts` is read-only and private-key directories are not mounted. The SSH capability is not authorization: pushes and deletions keep their normal approvals, and host verification is never weakened.
- **No D-Bus.** The session bus reaches `systemd --user`, which can start units outside the jail. OMP's direct desktop notifications are therefore unavailable inside the jail.
- **Jails refuse to nest.** Each jail sets `AGENT_JAIL`, and a launcher that sees it exits with a pointer to `hc run`. A nested launch half-worked before: `claude` failed on its read-only state directory, and `omp` started without `~/.omp`, so it had no login or config.
- **`rm` and `rmdir` are rmtrash, and trash is per mount.** Each writable path is its own bind mount, so deletions land in that mount's `.Trash-1000` (a rename into the home trash would fail with `EXDEV`). That is why `programs.git.ignores` contains `.Trash-*/`. `~/.local/share/Trash` is deliberately not bound.
- **Host containers.** `_mk-jail.nix` exposes the rootless Podman socket through `DOCKER_HOST` for Docker API clients and `CONTAINER_HOST` for the Podman-backed `docker` CLI. The Podman aspect already enables the user socket through `sockets.target`. The launcher mounts its directory rather than its inode so socket replacement remains visible. A read-only socket mount does not limit API authority; agents can manage host containers and container bind mounts resolve on the host. Jail-private `/tmp` files are not usable as host container bind sources. See [Podman's API service](https://github.com/podman-container-tools/podman/blob/main/docs/source/markdown/podman-system-service.1.md).
- **GitHub CLI and pnpm storage.** The shared launcher creates and binds each tool's data, cache and state directories read-write, including pnpm's store and global installs. It honors the XDG roots and `PNPM_HOME`; GitHub configuration remains read-only and honors `GH_CONFIG_DIR`. See [GitHub CLI path resolution](https://github.com/cli/go-gh/blob/trunk/pkg/config/config.go) and [pnpm store settings](https://pnpm.io/settings#storedir). Project-specific store paths outside these mounts still need a workspace bind or a grant. Shared caches are writable host state, not disposable sandbox copies.

After changing these mounts, rebuild and start fresh harness sessions. Existing jails keep their old mounts and environment. Verify with `gh extension list`, `pnpm store path` inside the project's development environment, and `docker info`. If the container API cannot connect, check `systemctl --user status podman.socket` on the host. A focused mount smoke test should also replace a temporary Unix socket while the jail remains open and verify persistent writes under both default and overridden storage roots.

### Core sidebar reporting

For App terminals, the launcher starts a per-launch bridge in `_herdr-relay/server.py` accepts only `activity.report` snapshots. It constructs Core label requests itself, with a fixed terminal and display namespace. Agents cannot select a different target or invoke other Core methods through it.

`HERDR_ACTIVITY_SOCKET` points to that endpoint inside the jail. The collectors use it rather than the Core socket, because the bridge owns the per-terminal lock, the session epochs and label cleanup. The launcher removes legacy Herdr identity variables. A missing host Core endpoint or an existing reporter lock aborts launch. Core reporting logs live beside the host-query logs.

The bridge clears its label on normal exit and stops when its launcher exits. Renderer leases cover crashes where cleanup cannot run. This is metadata transport only.

### Signing and push grant

Autonomous runs need children that commit and push, and children have no host access. The grant gives a session a separate agent SSH key for both, without exposing the user's GPG key.

- **The user grants it at launch** with `AGENT_JAIL_SIGNING=1 claude` (or `omp`). The launcher starts an ssh-agent on the host, loads the sops secret `agent_ssh_key`, and binds only the agent socket into the jail as `/tmp/agent-ssh.sock`. The jail can use the key, never read it.
- **Git is configured through the environment** (`GIT_CONFIG_COUNT`), which has command-line precedence over the read-only Home Manager config: `gpg.format=ssh`, `user.signingkey=key::<public key>` (ssh-keygen then signs through the agent), and `gpg.ssh.allowedSignersFile` for `git verify-commit`. SSH pushes find the key through `SSH_AUTH_SOCK`.
- **A granted session passes it on by variable.** `hc run -- env AGENT_JAIL_SIGNING=1 claude …` grants the child. Nothing enforces that only granted sessions do this, since any jail can reach Core; `git-conventions` limits it to granted sessions whose worker ticket asks for signing or pushing.
- **Setup.** `agent-jail/agent-ssh-key.pub` holds the public key, and GitHub lists it as both an authentication key and a signing key. Without that file or the secret, a grant prints a warning and the session runs ungranted. Agent logs live in `$jail_state/log/agent-key-<pid>.log`.

The key authenticates as the user's GitHub account, so a granted session can push to any repository that account can push to. Branch protection is what keeps agents off protected branches.

### `host_*` tools

`host_exec`, `host_mount`, `host_journal`, and `host_ssh_agent` provide approved host access from the jail. Herdr separately starts programs on the host through Core and App. host-query serves the `host_*` tools on a Unix socket bound only into its own jail (`/tmp/host-query.sock`), and both harnesses prompt on every call. `host_exec` runs one command unsandboxed; `host_mount` bindfs-grants a host directory at `~/granted/<name>`; `host_journal` reads the journal with a fixed argv; `host_ssh_agent` relays the SSH agent. Outside the jail `HOST_QUERY_SOCKET` is unset and all four short-circuit.

`host_journal` exists because the user namespace cannot map supplementary groups, so the `wheel` membership the journal ACL needs is gone. In-jail `journalctl` prints "No journal files were found" and exits 0, a silent-success trap.

The shared `agent-jail/jail-context.md` requires sandbox bash for ordinary CLI work, including GitHub queries and `gh auth status`. Authentication alone does not justify `host_exec`; escalation needs a concrete unavailable capability, supported by an error or a documented jail boundary.

If a `host_*` tool misbehaves, read `~/.local/share/<name>-jail/log/host-query.log` (bound read-only into the jail).

## oh-my-pi (omp)

`modules/programs/omp/`. omp has no sandbox of its own: its approval system is policy, not containment, so on Linux it runs in the shared jail.

OMP and terminal-browser use the same `llm-agents` flake input as Herdr, without overriding its nixpkgs, so their upstream store paths remain eligible for `cache.numtide.com`. Updating that input updates all its consumers.

The Nix overlay disables OMP's built-in browser prelude in favor of the shared terminal-browser CLI workflow.

- **Not the upstream HM module.** Its `package` is not nullable (the jail installs `omp`) and it writes only `config.yml`.
- **Settings go through `PI_CONFIG_FILES`**, set by `wrapProgram`. omp rewrites `~/.omp/agent/config.yml` from `/settings` and migrations, so that file cannot be a store symlink. The overlay ranks above global and project config and is never written back. Overlays replace arrays, so the pinned empty `extensions` stops a project from adding packages. Keys the overlay omits stay omp's, except the models below.
- **Everything else is `home.file`** under `~/.omp/agent/`. Read-only symlinks work because only `/mcp add|enable|disable` rewrites them, and that is not used. Extensions load from store symlinks: the loader resolves realpath, Bun imports `.ts` directly, and `@oh-my-pi/*` imports resolve to bundled copies, so no `node_modules` is needed.
- **All runtime state is under `~/.omp`** (credentials and MCP OAuth tokens in `agent.db`, sessions, worktrees), hence the single read-write bind.
- **Provider**: OpenAI Codex, logged in at runtime with `/login openai-codex`. Do not use `/login anthropic`: it works by impersonating Claude Code's client.
- **Shared prompts**: omp has no `` !`cmd` `` injection, so `omp.nix` strips the markers from shared commands and tells the model to run them.
- **Models**: roles and per-agent overrides are in `omp.nix`; overrides win over agent frontmatter. They stay out of the overlay so a repo's `.omp/config.yml` can replace them: the `omp-models` activation merges them into `config.yml` with `yq`, which puts them in the global layer, below project config. A project file that sets only some roles leaves the rest on Codex. This repo's `.omp/config.yml` points every role at Ollama Cloud through the built-in `ollama-cloud` provider, which reads `OLLAMA_CLOUD_API_KEY`. Cloud ids carry their tag before the thinking level (`deepseek-v4-pro:0813:high`); omp splits the level at the last colon. Ids come from the bundled catalog, which Codex replaces with its live `/models` list after login, so a missing id shows up as a role fallback in `/models`. Start on the slow role with `omp --model @slow`.
- **`bash.gitGuard = false`** lets skill ownership agreements permit branch switching. Shared bash rules and host, SSH, MCP and Nix approvals still apply. `herdr-app` asks on both platforms; other explicit Herdr prompts remain on Darwin.
- **Keybindings** in `omp.nix` move OMP actions off chords captured by Herdr App and OmniWM.

### Approvals

- `_bash.nix` overrides must only narrow toward ask or deny. omp resolves `bash.patterns` by first match, so `_permissions.nix` emits deny, then prompt, then allow. Claude resolves deny > ask > allow. Either way, a widening override would silently stop working.
- Jailed: `approvalMode = yolo`, because the jail is the boundary. Darwin: `approvalMode = write` plus the unjailed allowlist.
- The `host_*` tools are `tools.approval: prompt`. Explicit prompts hold even in yolo and never offer "approve for session".
- Subagents always run yolo, but deny and prompt still apply (a prompt rejects).
- `eval` is not gated in the jail: it reaches no more than bash already can.
- **Work MCPs go through `extensions/gate.ts`.** Approval keys are exact names without wildcards, and the work servers add tools upstream, so an exact list would silently allow new writes. `gate.ts` passes read verbs and confirms everything else. Without a UI it blocks, so an omp subagent can never write to Linear, Notion, or Datadog. This is stricter than Claude, which fully allows Datadog.

### Work MCPs

`modules/services/work/work.nix` (laptop only) adds Notion, Linear, and Datadog to omp through the `omp.mcpServers` option, plus the `troubleshoot` and `tickets` agents (limited to `omp.readOnlyTools`) and the `datadog-queries` skill. OAuth runs with `/mcp reauth <name>`; the callback listens on `:3000` inside the jail, which shares the host network. The omp `tickets` agent gets a preamble telling it to return each mutation as a proposal, because `gate.ts` blocks its writes and the parent session must perform them.

## Claude Code

`modules/programs/claude-code/`, configured through home-manager's `programs.claude-code`.

- **Skills** also come from other modules through `programs.claude-code.skills`: local `herdr-app` and `herdr-core` copies from `herdr.nix`, and the local jgrep copy from `work/jgrep.nix`.

## Work Hermes (laptop and macmini)

The `hermes-work` aspect includes `_work.nix` on both hosts. Its `hermes` wrapper runs Hermes directly. Linux uses a user gateway service and the official bubblewrap terminal backend. macmini uses local execution and the existing household system LaunchDaemon; no second gateway service is installed. The omp and Claude Code jails are unchanged. See [Voice services](voice-services.md#hermes-agent) for macmini's household profiles.

### Roles and task flow

`_models.nix` owns primary model/provider records by host and profile, including the default gateway and macmini's household profiles. `_fallbacks.nix` owns each profile's ordered fallback chain in Hermes's `provider`/`model` format; an empty list disables fallback. Linux work profiles cross between Codex and Claude subscriptions. macmini stays on loopback Ollama, changing models rather than providers. Utility models follow the host's default; decomposition follows its coordinator. Advanced delegation uses named profile routes, not model routes. Every role has the `delegation` toolset and may spawn plain subagents, which run as the same profile. Only the reviewer, coordinator and default use profile routes: a route lends the target profile's credentials, so the programmer never routes to the reviewer's GitHub token.

Cards carry the `Repo`, `Tracker` and `Git` rows served by `board_template`. Creation requires an existing checkout under `~/dev` or the configured extra repositories. The board MCP and native creation hook set `workspace_kind=dir` and the explicit checkout path. On the bubblewrap backend that path does not become the terminal's directory: every session, kanban workers included, starts in its profile's `terminal.cwd` (`~/dev/.hermes-workspaces/<profile>`), because Hermes moves `TERMINAL_CWD` only for `cwd_explicit` sessions and host-cwd backends. The laptop's coordinator and role profiles therefore bind all of `~/dev` read-write, and `souls/_linux.md` tells workers to `cd` to the Repo checkout (it persists between commands) or pass it as `workdir`. Tradeoff: those profiles can read and write every repository under `~/dev`, `.git` included, so a sandboxed command can plant hooks or config that the user's own Git later runs. On macmini the local backend starts in the checkout. Dispatch concurrency is one because cards can share a checkout; raising it requires separate workspaces for concurrent writers. Existing cards with scratch workspaces need replacement cards with explicit checkout paths before direct execution; their history and files are not deleted.

Roles create assigned, non-triage work. Only an interactive coordinator conversation may explicitly request triage. Assistant-created cards remain blocked until a human authorizes them. Dependencies select `todo` or `ready`; `parents` are dependency edges, not a hierarchy. Decomposed children inherit the original card's directory and missing run settings.

The programmer verifies changes and requests review with an exact range. `skills/sdlc-review/SKILL.md` governs independent review, authorized publication and exact-head CI. Findings return to the programmer on the same branch and PR. Board completion does not imply merging or external tracker closure. Roles use native card comments, blocking and completion tools. Shared formatting requires abbreviated PR references in comments and handoffs.

A blocked card's reason is its whole explanation to the user: `_role.md` fixes a short `## ⛔ Blocked:` note, posted as the card's last comment and as the block reason, with evidence in an earlier comment. The user unblocks the card directly. No coordinator pass rereads blocks. The coordinator has `kanban_archive`, `kanban_delete` and `kanban_route` from `hermes-workflow`. `kanban_route` reassigns a card to a work role and releases it from `triage`, `blocked` or `todo` to `ready`: Kanban's own tools move only a worker's own card, so rework that `kanban_request_changes` returns to the coordinator otherwise sat blocked. Coordinator tool descriptions come from each handler's docstring; the plugin runs in Hermes, so they reach the board even though the terminal sandbox hides `~/.hermes` and the `hermes` CLI fails there with a read-only `.bootstrap.lock`. Git policy snapshots live in `~/.hermes/hermes-workflow.json`, protected by a file lock; its leftover `_checked` key from the removed blocker watcher is ignored.

### Git ownership

Each category—branches, worktrees, commits, pushes and PRs—is `agent` or `human`. Missing values and legacy `ask` values mean `human`. Background workers do not open permission dialogs: human-owned work produces a handoff.

The `git` tool accepts a task ID and an argument array, without an executable. It requires the current dispatcher-owned task, refuses delegated children and unrelated tasks, checks the checkout against the card, and snapshots its policy on first use. A subsequent metadata change fails closed until the user runs `hermes git-policy <task>` outside an agent terminal. Agents must not broaden grants when creating follow-up work.

`plugin/git_proxy.py` limits Git commands and options, disables hooks, external diff drivers and rerere, rejects executable repository configuration, and uses a fresh SSH agent containing only the dedicated agent key. It does not use the user's SSH agent or YubiKey. Commits are SSH-signed; pushes verify every newly introduced commit against the configured agent key or human GPG fingerprint. Pushes target an explicit branch and cannot force-update or delete refs. Fetches accept named GitHub remotes, not arbitrary URLs or refspecs.

Before each operation the proxy lists the repository's local config, plus `config.worktree` under `extensions.worktreeConfig`, without includes. The check is a deny list: `DENY` refuses keys that run a command, load other config or files, redirect URLs, supply credentials, move refs or the work tree, or loosen protections. A suffix rule (`*.program`, `*.command`, `*.cmd`, `*.textconv`, `*.driver`, `*.clean`, `*.smudge`, `*.process`, `*.helper`, `*.editor`, `*.pager`) catches drivers and tools in any section, so `filter.lfs.required` passes and `filter.lfs.smudge` does not. `VALUES` limits a few keys to safe values, such as `submodule.<name>.update` without `!command`. Every other key passes. Keys that the forced `-c` options override, such as `core.hooksPath` (forced to `/dev/null`, so Husky hooks never run), `rerere.*`, `user.*` and `commit.gpgSign`, pass because the override wins. Remote and submodule URLs must be credential-free GitHub URLs. A refusal names the key; the user removes it or runs that Git operation by hand. Every proxied command forces `rerere.enabled=false`, `rerere.autoUpdate=false` and `fetch.recurseSubmodules=false`, so resolutions the user recorded never enter agent merges and fetches never reach submodule URLs.

PR ownership is a workflow rule, not a Git protocol operation. Every role and the coordinator receive the managed GitHub token, for `gh` and the GitHub package registry. Hermes strips `GH_TOKEN` and `GITHUB_TOKEN` from terminal commands even when `env_passthrough` names them (`tools/environments/local_env_policy.py`), so the token travels as `AGENT_GH_TOKEN` and the patched bubblewrap plugin sets `GH_TOKEN` from it on every sandbox spawn. A `BASH_ENV` hook or a `gh` shim on `PATH` does not work: Hermes strips `BASH_ENV`, and nelly-mono's devshell ships its own `gh`. `gh auth status` inside a role's terminal verifies it. That token also permits direct GitHub API operations, including PR creation: the Git proxy does not constrain those APIs, so PR ownership rests on the souls.

- **Linux bubblewrap:** the network profile, default-deny home visibility, explicit secret hides and fail-closed backend startup. The profile workspace and sandbox scratch space are writable. Runs that never reached a worker session show disabled. ### Bootstrap and runtime setup

`_bootstrap_work.py` serializes startup and merges Nix-owned settings into writable profile configurations, preserving unrelated runtime configuration. Model records are replaced rather than merged, so changing providers cannot retain an old endpoint or API key. Both bootstraps remove the legacy `fallback_model` key when applying managed fallback chains, preventing obsolete routes from being appended. Bootstrap fails on malformed YAML or unmanaged profile directories; it can adopt directories containing only Home Manager's plugin links. The root gateway explicitly runs `hermes -p default gateway run` with profile multiplexing; unrouted chat uses the interactive default profile's tool allowlist. On macmini, the household bootstrap runs first; the work bootstrap preserves its root API-listener `.env`.

SOULs combine the role file, shared role rules where applicable, host execution policy, formatting and the shared `agent-shared/evidence.md`. Each role file and the coordinator's carries a **Required skills** trigger table, and `souls/_skills.md` makes those loads mandatory and visible: workers list them in a `Skills loaded` handoff row that the reviewer checks. `hermes-agent.nix` owns `disabledSkills` (bundled duplicates of house skills, plus `claude-code` and `codex`), which work and household profiles both apply. Bootstrap replaces that list, so a Desktop skill toggle lasts only until the next gateway restart. Work souls skip `agent-shared/context.md` and Caveman, which contradict `_formatting.md` or name harness mechanics; Ponytail is appended for the programmer only. `_role.md` tells Git workers that the proxy replaces `git-conventions`' credential and signing sections. The coordinator never pre-creates review cards: review stays on the programmer's card, so upstream's "complete to release the review child" branch never applies. `to-spec` and `to-tickets` stay manual for the coordinator too. Upstream Hermes injects its own Kanban protocol, including an "Orchestrator mode" section that reaches every worker; only a Hermes patch removes it. QA uses native browser tools rather than host Herdr launches.

Runtime setup includes authentication for the selected providers, chat channels and profile routes, coordinator MCP OAuth logins, and assistant Google login. Linux's default models need Codex authentication and a Claude CLI subscription login; macmini's defaults use the existing Ollama service. Linear, Notion and Datadog keep full MCP trust. The assistant has no terminal, delegation or Git tools; `google-login` grants only Gmail and Calendar read access.

Interactive CLI lifecycle still reports to Herdr through OSC 7501. Home Manager installs Desktop on both hosts, built from the managed package with `HERMES_DESKTOP_HERMES` set to the managed `hermes` wrapper, so its backend runs the same bootstrap, environment and version as the CLI and gateway. Upstream's `desktop` package starts its own build stamped `0.0.0`. Plugins gated by `requires_hermes` (bubblewrap, advanced delegation, Office 3D) refuse that version. Without bubblewrap the `bubblewrap` terminal backend is unknown, and Hermes then drops file tools along with the terminal. A backend log line `Plugin 'bubblewrap' skipped: requires hermes >=…, running 0.0.0` means Desktop is not running the managed backend. After plugin changes, restart the selected Desktop backend and reload the app; installing frontend files alone does not enable a plugin's backend API.

`_desktop-settings.nix` owns Desktop appearance preferences. Home Manager activation applies them with Hermes's native, locked preference writer to `~/.hermes/ui-preferences.json`. The file stays writable; unrelated preferences are preserved. Activation reapplies the global appearance and clears per-profile appearance overrides so every profile inherits it. Do not replace this file with a read-only Nix-store link.

Bot avatar PNGs live in `modules/services/hermes-agent/assets/`. `_work.nix` links each managed avatar into its profile's `assets/avatar.png`, with the default profile under `~/.hermes/assets/`. Every librarian profile, on either host, gets the librarian image. Change avatars in Nix rather than Desktop; an editor replacement can remove the managed symlink.

After activation, restart Linux's gateway manually (`X-RestartIfChanged=false`). Only one gateway runs per host. Hermes clients (Desktop, the CLI, cron and Kanban) start an installed unit named exactly `hermes-gateway.service` instead of spawning their own gateway (`hermes_cli/gateway_runtime_service.py`), so the unit keeps that name; under any other name Desktop spawned a gateway with its own environment and the unit failed with "The host gateway already serves profile 'default'". Desktop also launches the per-user profile's `hermes`, which tracks the current generation. Check with `pgrep -af 'gateway run'`: one process, in `hermes-gateway.service`'s cgroup. macmini retains `system/org.nixos.hermes-agent`; do not install a second user gateway. Reconnect board MCP clients so tool schemas refresh. Do not switch a running workload mid-task. Updating configuration does not stop external workers already running from earlier sessions.

For `Unknown provider` errors, check the actual running executable as well as `command -v hermes`. An older session keeps its old package and sandbox after activation. Relaunch through the current Home Manager wrapper, which selects the unwrapped Claude CLI; the old full-process Hermes jail does not expose the Claude login. Provider registration runs outside the current terminal-only bubblewrap backend.

### LLM wiki

Each host keeps a curated Markdown wiki, in the shape of the upstream `llm-wiki` skill, inside an Obsidian vault. Bronze is a tree's `raw/` folder, silver its `review/` proposals, and gold its approved pages. `wiki-gate/gate.py` states the per-folder write policy in its docstring.

`_wikis.nix` is the per-host tree table: each tree's vault, librarian, chat writer, domain, and `local` for a vault with no remote. Gate policy, souls, hwiki settings, cron jobs and sync jobs derive from it, so add or move a tree there. `programs/obsidian.nix` names the vault and trees itself for the Obsidian app and Web Clipper templates, so update it with any rename. Souls are templates: `_wikis.nix`'s `soul` fills `@tree@`, `@vault@`, `@domain@` and `@librarian@` into `souls/librarian.md` for librarians and appends `souls/_wiki.md` for writers.

On the laptop, `librarian` curates the `work` tree and talks to Augusto in its Bot Chat in Hermes Desktop. The coordinator files sources into `work/raw` and hands ingest, verdicts, apply and lint to the librarian through a profile route. The default profile and the roles get hwiki recall only: the gate's `recall_only` list blocks `wiki_memory_write`, `mirror_builtin_memory` is off, and their sandboxes have no vault bind. Default lives at `~/.hermes`, so `_work.nix` links its hwiki plugin and bootstrap writes its `hwiki.json` there. It gains the `memory` toolset for hwiki but no `OBSIDIAN_VAULT_PATH` or `WIKI_PATH`, because the root `.env` is loaded by the gateway process that serves every profile. The assistant has no wiki. The macmini's librarians are in [Voice services](voice-services.md#llm-wiki).

- **Librarians** have the `file`, `skills` and `memory` toolsets; hwiki's memory tool needs `memory`. They have no terminal and no Git. Only librarians load `wiki-skills/`: `llm-wiki` (vendored from Hermes `optional-skills/research/llm-wiki`; update it by hand) and `llm-wiki-review`. They also follow the shared `writing-for-agents` skill for proposals and pages, since agents read the wiki through recall. `_bootstrap_work.py` creates the `wiki-ingest`, `wiki-lint`, `wiki-memory` and `wiki-sync-report` cron jobs by name and updates only the fields Nix changed; `_work.nix` owns the schedules.
- **Delivery.** Every librarian cron delivers `bot-chat,all`: the librarian's own Bot Chat in Hermes Desktop, plus every channel with a home target connected at runtime. Nix manages no messaging platform for librarians. Augusto adds one by hand, such as Telegram with its own BotFather bot per profile and `/sethome` or the profile's `.env`, and `all` picks it up on the next run. A literal platform target would fail pre-dispatch validation until that platform has credentials; `all` and `bot-chat` skip that check (`cron/scheduler_preflight.py:_preflight_check_delivery`), and `all` with no home channel resolves to nothing while `bot-chat` still delivers (`cron/scheduler_delivery.py:_resolve_delivery_targets`). Answer a digest with verdicts in the Bot Chat or in the connected channel.
- **Bot Chat turns.** Hermes delivers to Bot Chat as an inbound turn that tells the bot to "Review it, act on anything that needs action, and summarize for the chat" (`cron/scheduler_delivery.py:bot_chat_message`), and each delivery costs the librarian one turn. `llm-wiki-review` says how the librarian answers it, and that turn never carries a verdict. Delivery needs the librarian's gateway authority ready; otherwise the output is parked under `cron/bot_chat_pending` and admitted on a later tick. Bot Chat runs show `delivery_queued` until the bot accepts the turn, and a `no_agent` job's run stays `delivery_queued`.
- **Sync reports.** `hermes send` reaches messaging platforms only, so no script can post into Bot Chat. A failing sync writes its message to `.git/vault-sync-report` in the vault and deletes it on the next successful run. The librarian's `no_agent` cron job `wiki-sync-report` prints that file at 5, 20, 35 and 50 past each hour and delivers it like the other crons, so a failure repeats every quarter hour until a sync succeeds; an empty file is a silent run. Hermes keeps the newest 50 run files per job; the timer also writes each failure to the journal or launchd log. The bootstrap copies the script into the profile's `scripts/` because cron refuses scripts that resolve outside it, including store symlinks.
- **hwiki** reads per-profile settings from `$HERMES_HOME/hwiki.json`, because its environment overrides are process-wide and one gateway serves many profiles. Bootstrap merges Nix-owned keys over local ones.
- **Gate.** `_wiki-gate.nix` renders the plugin's `settings.json` per host from `_wikis.nix`; the other host's trees in the same vault stay read-only. The `pre_tool_call` hook gets no profile argument, so it reads the context-local Hermes home that `profile_routes` sets for a delegated child. `HERMES_HOME` names the gateway's profile instead.
- **The terminal gap.** The hook sees only `write_file` and `patch`. Terminal and code-execution writes bypass it. On the laptop, the bubblewrap backend narrows the gap: the coordinator's sandbox binds only `work/raw` writable, the librarian's only `work`, and roles get no vault bind. File tools run in the same sandbox, and `.git` stays unreachable, so no sandbox can plant Git hooks or config that the sync job would run. macmini terminals are unsandboxed and can write anywhere. On the laptop the sync audit catches what the sandbox lets through. On the macmini it does not: the `augusto` and `livia` terminals can commit with the `manual:` prefix, which the audit skips, or write a proposal marked applied. There, gold rests on the gate hook and on those profiles following their souls.
- **Delegated toolsets.** A `delegate_task` child routed through `profile_routes` keeps the delegating profile's enabled and disabled toolsets; `profile_home` swaps only scope, model, SOUL and credentials (`tools/delegate_tool_toolsets.py:_resolve_child_toolsets`, `tools/delegate_tool.py:262,279` in the locked hermes-agent). Librarian work delegated from the coordinator or from `augusto`/`livia` therefore runs with their terminal, web, code_execution and Git, and on the laptop that terminal sits in the librarian's writable `work` bind, outside the gate hook. Only the librarian's own chats, Desktop sessions and crons are limited to `file`, `skills` and `memory`. This is an accepted risk; the audit above is the laptop's backstop.
- **Memory maintenance.** Agents file dated bullets into a tree's `memory/` through `wiki_memory_write`, and recall reads them at once with no review. The weekly `wiki-memory` cron has the librarian merge, drop and restructure those files by itself, with no proposal or verdict; the gate lets file-tool writes into `memory/` through only for that tree's librarian. hwiki rewrites `memory/builtin-mirror.md`, so the skill keeps it untouched. The job never writes gold; it lists promotion candidates in its report, and the digest stays the only path to gold. The audit treats `memory/` as non-gold, so these edits sync without a proposal.
- **Approval.** The librarian records verdicts itself, so a prompt-injected raw source could make it mark a proposal approved, and the gate and audit would accept the result. Human approval rests on the instructions in `wiki-skills/llm-wiki-review`.
- **Sync and audit.** `_vault-sync.sh` (`vault-sync <vault> <tree>`) runs on a schedule set in `_work.nix`: the `wiki-sync` systemd user timer on the laptop, the `wiki-sync-<tree>` launchd agents on macmini. Librarians have no Git, so the job also writes each tree's baseline, including the `.gitignore` and `review/inbox.base`. It stages everything, runs `gate.py audit`, commits, fetches, rebases onto the remote branch, and pushes over HTTPS with the SOPS `github_token`. When the remote has no branch yet, such as a new empty GitHub repo, the push creates it and sets tracking. The audit covers staged changes plus unpushed commits. Until the branch tracks a remote branch, it covers staged changes only, so commits made before the first push are not audited. Every changed gold page needs an applied proposal for it in the same change set. A gold change whose proposal in `review/` is still `approved` is an apply in progress: the job leaves that page uncommitted until the next run and reports nothing. A failed audit commits nothing. A rebase conflict aborts the rebase and keeps the local commit unpushed. Each failure stays in the sync report until a run succeeds; the job keeps retrying. A rebase already in progress pauses sync until resolved by hand. A vault with no Git remote, such as the `local` one, commits only. The job decides that from `git remote`, because a fresh remote has no `@{upstream}` ref to resolve. A branch without tracking config syncs with the vault's only remote and gains tracking on the first push. A detached HEAD, or several remotes and no tracking config, pauses sync with a report.
- **Manual edits.** obsidian-git commits carry the `manual:` prefix, which `_wiki-gate.nix` also passes to the audit, and the audit skips those commits. obsidian-git therefore never auto-commits or auto-pushes: a prefixed automatic commit would carry pending agent writes past the audit. A hand commit of all changes does the same to whatever is pending, so check its diff first.
- **Vault checkout.** Clone Augusto's vault over HTTPS before the first Home Manager switch that includes `obsidian`: `git clone https://github.com/augustocdias/obsidian-vault.git ~/obsidian-vault`. Activation creates `~/obsidian-vault/.obsidian/`, and `git clone` refuses a nonempty target. If a switch already ran, move the generated `~/obsidian-vault` aside, clone, and switch again; activation rewrites `.obsidian/`. Until `.git` exists the sync job does nothing. The `wiki-vaults` activation runs `git init` for `local` vaults.

Verify the wiki with these commands:

- `python3 ~/.hermes/plugins/wiki-gate/gate.py audit <vault> [--base REV]` audits by hand. Exit 0 passes, 1 lists gold changes without an applied proposal on stdout, and 2 is a usage or configuration error.
- Laptop: `systemctl --user start wiki-sync.service`, then `journalctl --user -u wiki-sync`. `systemctl --user list-timers wiki-sync.timer` shows the schedule.
- macmini: `launchctl kickstart -k gui/$(id -u)/org.nix-community.home.wiki-sync-<tree>`, then read `~/Library/Logs/wiki-sync-<tree>.log`.
- `hermes -p <librarian> cron list` shows the ingest, lint, memory and sync-report jobs; `hermes -p <librarian> cron runs <job>` lists runs. A profile's rendered `config.yaml` names `hwiki` as its memory provider, and its `hwiki.json` holds the wiki root, memory folder and untrusted folders.
- End to end: send a source in a chat, run `hermes -p <librarian> cron run wiki-ingest`, read the digest in the librarian's Bot Chat, approve one proposal and say "proceed with the approved revision". Only the approved page should change in gold, and the next sync should commit and push it.

## rtk (shell-output compression)

`modules/programs/rtk.nix` (aspect `rtk`, in `user-base`) installs nixpkgs `rtk`, the full edition with the BUSL `engine` feature. No `pipeline.toml` is written, so it runs `rtk:default`: the bash rewrite plus per-command filters.

- **Claude**: a `PreToolUse` hook on `Bash` runs `rtk hook claude`, which rewrites supported commands (`git status` to `rtk git status`) through `updatedInput`. rtk returns `allow` only when one of our allow rules matched, and Claude still applies its deny and ask rules over a hook `allow`.
- **omp**: `~/.omp/agent/extensions/rtk.ts` is upstream's extension from `pkgs.rtk.src`, version-matched to the binary. It rewrites the command in place.
- **Rule twins**: Claude checks permission rules against the rewritten command, and omp's order is unverified. So `_bash.nix` gives each pattern not starting with `*` an `rtk <pattern>` twin with the same action. Without twins, `rtk nix run …` would slip past `nix run*` and land on the jailed `*` allow.
- **Hermes**: every profile on both hosts enables upstream's `rtk-rewrite` plugin from `pkgs.rtk.src`. `_work.nix` links it for the work profiles and the root, and `_darwin.nix` for the household profiles. The plugin finds `rtk` on the Hermes process's `PATH` and skips hook registration with a stderr warning when it is missing. Its `pre_tool_call` hook edits the `terminal` command before Hermes's approval floors run, so `approvals.deny` sees `rtk git status`. The work profiles therefore carry `rtk git` and `rtk git *` twins beside the Git denies. The rewritten command runs in the terminal backend, which inherits the same `PATH`; on the laptop that is the bubblewrap sandbox, where `/etc/profiles/per-user/augusto/bin` stays visible. The sandbox hides `~/.local/share/rtk`, so Hermes commands add nothing to `rtk gain`; rtk still exits normally.
- **Never run `rtk init`**: it would patch the immutable `settings.json` and the Nix-owned extension.
- **Stats**: `~/.local/share/rtk` is bound read-write in the jail, so `rtk gain` persists. The home-manager activation creates the directory, because the jail skips a missing bind source.

- After changing `_bash.nix` or a harness `_permissions.nix`, inspect the rendered rules (Claude's `settings.json`, omp's `PI_CONFIG_FILES` overlay), not only the source.
- Keep `jail-context.md` (agent-facing sandbox contract) and `agent-shared/context.md` (cross-platform routing) as the always-loaded owners. Put detail here, not there.
